1.23.0 2026-09-22 目前版本

BIOS 裡的 CPU microcode 也列進 SBOM

PC BIOS 帶著主機板支援的每一顆處理器的 microcode,而 Intel 的 安全公告正是以 microcode 版本來寫的。現在每個 microcode 更新都成為 SBOM 裡的 一個元件,帶著它的 CPUID 與版本 —— 正是 CPU 漏洞比對需要的兩項資訊。

修正:BIOS 裡的 microcode 不再被當成「無法分析」

microcode 本來就是加密的,以前單看位元組會把它誤判成無法分析的區段。現在以它 的結構辨識,正確列為元件。

每份 SBOM 也多了一行格式描述,例如「U-Boot FIT image + SquashFS 4.0 (xz)」,由實際解析到的結構寫成;Windows 版以前這一欄一直是空的。

一次處理一整批韌體

CRA 要的是可以持續重跑的 SBOM 流程,而一條產品線常有幾十個韌體版本。現在可以 一次拖入多個檔案或整個資料夾:逐個分析、每個檔案一列狀態, 完成後一鍵下載 ZIP,裡面是每個檔案的 SBOM、證據報告,以及一份 可以用 Excel 打開的摘要表。

命令列也有同樣的功能(--batch),方便接進自動化流程: 一個檔案失敗不影響其他檔案,摘要會寫明原因。

大檔案的記憶體用量大幅下降:上傳一邊到達一邊處理,不再先整份讀進來再複製。 檔案仍然不會寫入磁碟。

讀得懂 ext4 與 YAFFS —— eMMC 設備與舊款 NAND 攝影機

韌體放在 eMMC 等區塊裝置上時(NVR、閘道器、x86 設備),root filesystem 幾乎都是 ext4。現在 ext2 / ext3 / ext4 都讀得出來;加密的檔案會逐個標示為 無法分析,而不是默默略過。以 OpenWrt 官方 x86 映像驗證:1,069 個檔案與同版本的 SquashFS 逐位元組比對,零差異。

較舊的 NAND 攝影機、DVR、機上盒常用 YAFFS。這種映像不記錄自己的 格式參數,所以會逐一嘗試、找出讀得通的那一組。公開的 79 個測試樣本全部讀出。

整個磁碟映像再用 gzip 壓縮的更新檔(例如 OpenWrt 的 x86 映像)現在會解開後 再往裡面讀一層,分區表與各分區的檔案系統都會被找到。

讀得懂 FIT 與 initramfs —— 新一代 router 與攝影機的開機映像

FIT(.itb)已取代大部分 ARM 板子上 的舊式 uImage。它會自己說明每個映像是甚麼、用甚麼壓縮,並附上 hash。現在會 照它的說明解開 kernel,並重新計算每一個 hash —— 不符就報告 映像在建置後遭到損毀或修改。

很多韌體把整個 root filesystem 做成 initramfs,放在 FIT 的 ramdisk,或直接編進 kernel(攝影機常見)。現在兩種都讀得出來,包括裡面的 套件資料庫。

實測:OpenWrt 23.05.5 官方 recovery 映像

以前只得到 9 個元件,大多沒有版本,kernel 整段被判為無法分析;現在得到 154 個,包括 147 個套件的精確版本與 Linux 5.15.167。

OpenWrt 在映像結尾附上的版本資訊(版本、revision、board)也會寫進 SBOM, 即使 root filesystem 讀不到,也能說明這是哪一版韌體。

讀得懂 UBI / UBIFS —— NAND flash 上的韌體

NAND flash 上的韌體很少直接就是一個檔案系統,而是 UBI: 一連串 erase block,各自說明屬於哪個 volume 的第幾個邏輯區塊。現在會把 volume 按裝置的規則拼回來 —— 區塊次序打亂也可以,同一區塊有新舊兩份時 新的勝出 —— 再把裡面的 SquashFS、CramFS 或 UBIFS 照常讀出。

UBIFS 依它自己的 index 讀,而不是掃描 flash 上每一個節點: 掃描會把已刪除的檔案一併讀回來,SBOM 就會列出裝置上根本沒有的軟體。

修正:讀不到的單一檔案不再默默消失

以前檔案系統裡解壓失敗的檔案只會被略過 —— 沒有掃描,SBOM 裡也完全沒有它。 現在每個有檔案讀不到的檔案系統都會記為 opaque 元件,寫明 是哪些檔案、為甚麼讀不到。

修正:根檔案系統依內容選擇

UBI 映像裡「configuration」volume 可能排在「rootfs」之前。現在會選有 os-release、套件資料庫或 busybox 的那一個,而不是固定取第一個。

讀得懂 JFFS2 —— 攝影機與 router 的可寫分區

JFFS2 是 raw flash 上的可寫檔案系統:OpenWrt router 的 overlay、 大量攝影機與工業裝置的設定與應用程式分區。它不是一次建好的映像,而是一份 日誌 —— 檔案每改一次就追加一批節點,最新的版本勝出。所以 一個檔案要由所有曾經寫過它的節點重新組出來。

最重要的一點:刪除檔案也是寫一個節點。忽略它,裝置刪掉的 每個檔案都會「復活」,SBOM 會列出裝置上根本不存在的軟體 —— 而且下游完全 察覺不到。這個 reader 會正確處理刪除。

標準函式庫沒有 LZO 解壓,所以一併附上純 Python 實作。它對照一個獨立的 C++ 實作做過差分測試:258 個輸入、5.9 MB 資料(大部分是真實韌體內容), 零差異。

修正:flash dump 裡 rootfs 之後的檔案系統沒有被掃描

從裝置直接讀出的 flash dump 通常有一個唯讀 rootfs,後面跟著一個可寫的 overlay。以前只有第一個檔案系統會被分析,第二個整個不會被 掃描 —— 出廠後才安裝的套件就跟著一起消失。現在每個檔案系統都會逐檔掃描。

看得到分析做到哪一步

拖檔案進去之後,頁面會顯示目前在哪一個階段、做到哪裡 —— 「解析執行檔 546 / 3274」、「判斷區段 2 / 4:Linux kernel (lzma)」—— 以及已經用了多少時間。

進度條只在真的做完某件事時才前進,從不靠計時器推。 一條自己慢慢爬、然後卡在 90% 的進度條,是為了讓等待感覺短一點而說的 小謊。它也只會往前、不會倒退,而且只顯示已用時間,不顯示預估 剩餘時間 —— 同一個階段在 router、BIOS、攝影機韌體上花的時間 差好幾倍,任何剩餘時間的估計都只是猜測。

修正:網頁漏掉了沒有套件資料庫的 Linux 韌體元件

從 v1.9.0 起,逐一掃描 root filesystem 檔案的功能只有命令列版 有,網頁版從來沒有。任何沒有套件資料庫的 Linux 韌體 —— 大部分 CCTV / NVR 韌體就是 —— 在網頁上會漏掉所有從 檔案系統裡找到的元件。

如果你之前用網頁分析過這類韌體,請用這一版重跑。 現在命令列、網頁與測試共用同一條分析流程,不會再各自分歧。

修正:Linux 映像的架構顯示成「未識別」

網頁只看檔頭層級的判定,所以一部 MIPS router 顯示「未識別」,但下載到 的文件裡寫得清清楚楚。現在會和命令列一樣,從檔案系統裡的程式讀出架構。

認得廠商包在外面那層,以及裡面的 CramFS

消費級 router 的韌體下載檔很少是裸映像,而是映像前面加了廠商自己的檔頭。 檔頭很小,後面就是我們本來就讀得懂的韌體 —— 所以一個 .trx 檔與一份完整 SBOM 之間,差的只是「知道要跳過 32 個位元組」。

容器常見於
Broadcom TRX v1 / v2Netgear、Linksys、Asus、Buffalo
Netgear CHKNetgear（裡面通常包一個 TRX）
D-Link SHRSD-Link
Instar BNEGInstar IP camera
Moxa FRMMoxa 工業閘道器

它不解壓任何東西 —— 認得容器、記下檔頭說了什麼,其餘交還 原本的流程。兩件刻意不做的事:不猜 payload 位置(切錯位 置不會大聲失敗,只會讓後面每一項發現都偏移幾個位元組,然後安靜地產生垃圾); 不假裝加密的 payload 讀得到(D-Link SHRS 在實機上是加密的, 認得外層不會改變這件事)。

CramFS 是很多攝影機、機上盒與較舊閘道器在 router 用 SquashFS 的位置上用的東西。新的 reader 提供與 SquashFS 完全相同的介面, 所以套件資料庫讀取、ELF 依賴分析、逐檔簽章掃描全部照跑,一行都不用改。

驗證方式值得一提:公開樣本同樣的內容有大端與小端兩份,所以兩個 decoder 是 互相驗證,不只是各自對照規格書。12 個變體全部讀出完全相同的 檔案清單與內容。

修正

未識別的區段被標成「已解開」。那個旗標的意思是「無論熵值 多高,這一段我們讀得懂」—— 於是任何不屬於已知容器的高熵區段,都 會因為「我們有它的位元組」而被判成明文。一個加密的 D-Link 韌體 payload,熵值 7.951,就這樣被報成 plaintext。

這是上一版那個問題的同一個錯誤,但在最常走的那條路上。 如果你分析過任何含有加密區段、而外層容器我們當時不認得的韌體, 值得用這一版重跑。

PC BIOS:123 個模組,而字串比對一個都找不到

BIOS 是唯一一類字串比對幾乎找不到任何東西的韌體。一份 公開的 EDK2 映像,整整 4 MB,我們資料庫裡 36 個簽章一個都沒有 命中 —— 沒有 OpenSSL banner、沒有版本字串、什麼都沒有。

但它有另一樣東西:build 系統自己寫進去的清單。每個模組都帶著自己的名字, 名字被剝掉的還有 GUID 精確指認。同一份映像跑出 123 個模組, 119 個有名字。

來源內容Confidence
USER_INTERFACE section模組名稱,build 當時怎麼叫它就是什麼0.97
檔案 GUID名稱被剝掉時仍然精確指認0.90
PE 檔頭指令集(x86-64 / IA-32 / AArch64 / RISC-V)宣告值

而絕大部分都藏在一層壓縮後面。實測:1.4 MB 解開變成 16 MB,123 個模組裡有 112 個在裡面。不解壓縮的工具看到十幾個模組,就當 自己讀完了一份 BIOS。解開的內容也會照樣跑字串比對 —— 那份映像唯一命中的 元件(OpenSSL)就只在解壓後找得到。

Management Engine 不會被當成韌體的一部分。你從 PC 上 dump 出來的通常是整顆 SPI flash,裡面除了 BIOS 還有 Intel ME —— 簽章過的 Intel 程式碼,Intel 以外沒有人讀得懂。把整個檔案一起量,等於把兩件不同的 東西平均起來,結果哪一件都不描述。現在依 descriptor 切開,ME 照實報成 「無法列舉」。

三件事是刻意不做的:不為 UEFI 模組生 purl(它不是任何 生態系裡的套件,硬生一個等於餵給 CVE 比對一個世上不存在的識別碼);模組的 VERSION section 會標明那是模組自己的版本、不是函式庫版本(EDK2 幾乎永遠 寫 1.0);EFI/Tiano 壓縮認得但解不開,這類區段會明確報告讀不到 而不是略過 —— 略過會讓清單靜靜變短。

修正

只是「切出來」的區段被標成「已解開」。那個旗標的意思是 「無論熵值多高,這一段我們讀得懂」。但 ESP32 的 partition 與 UEFI 的 flash region 只是從檔案裡切一段出來,不是解壓出來的。後果是加密 的 ESP32 partition、或 Intel ME 區,會因為「我們有它的 bytes」而被判成 明文。ESP32 那條路徑同樣受影響,一起修了。

剛列完 123 個模組,標題卻寫「無法靜態識別元件」。 調和那個矛盾的函式只看得到簽章命中與套件資料庫,看不到由結構讀出來的 元件。現在兩者都算。

真實韌體教的兩件事

合成測試檔是照規格寫的,這兩個缺陷它們一個都看不出來:pad file 的 GUID 是全 0xFF,和抹除過的 flash 一模一樣 —— 用 GUID 判斷 volume 結尾,會在第一個 pad 停下來,真實映像裡整個 PEI volume 的模組 就這樣消失了。還有存放 UEFI 變數的 NVRAM 區與模組區共用檔頭, 當成模組區來讀會憑空「生」出一個不存在的模組 —— 真實映像第一次跑就生了。

加密的韌體:在介面裡直接比對廠商 SBOM

映像一旦加密,裡面的元件就在密碼後面,再聰明的靜態工具都讀不出來 —— 這不是我們的限制,是所有同類工具的限制。唯一的出路是向供應商索取他們 自己的 SBOM,而 CRA 下製造商本來就有權這樣要求。

這個功能一直都在,但只有命令列版有 —— 而最需要它的那批客戶(CCTV、專有 SoC 裝置),正好就是最不會碰命令列的那批。現在拖拉頁面的下載區下方就有 「廠商 SBOM(選用)」,拖 CycloneDX 或 SPDX JSON 進去即可,可以 同時放多份:一個產品往往不止一個供應商,把它們合併成一份就分不出 哪一句是誰講的。

但匯入不是把兩份清單接起來,而是逐項比對:

結果意思
獲映像佐證廠商說有,映像裡也找得到
版本衝突廠商聲明的版本,與映像裡實際編進去的不同
未觀察到廠商說有,但映像裡找不到 —— 這不代表不存在

衝突排在最前面並用紅色標出。廠商聲明的版本與映像裡編進去的不同,是整個 比對功能存在的理由 —— 把它埋在一堆「一致」的統計數字下面就浪費了。

讀不到的廠商檔案會單獨列出原因,不會靜靜略過:「0 個衝突」與 「我們根本打不開你供應商那份檔案」在畫面上看起來一模一樣,除非 後者講出來。而且它不會連累你本來要做的韌體分析。

上傳的廠商 SBOM 與韌體一樣只存在於記憶體裡,不寫入磁碟、不離開這台機器。

順帶補上頁面文案:輸入格式其實早就支援 .hex、.s19、 .uf2、.elf、ESP32 映像與整顆 flash dump,但頁面 一直只寫著 .bin。

修正

沒有 purl 的廠商 SBOM 比對不到任何東西。比對只用 purl 當識別鍵,但供應商自己產生的 SPDX 很常沒有 purl。結果是整份文件都被歸成 「聲明了但未觀察到」—— 看起來像一切正常,實際上是根本沒比對成功。現在 purl 與名稱都會用來配對。如果你之前匯入過廠商 SBOM 而結果是「全部未觀察 到」,值得用這一版重跑一次。

套件現在由腳本產生,而且是可重現的:entry 排序、timestamp 與壓縮等級全部固定,所以同一個原始碼版本重新打包會得到位元組完全相同的檔案。 下載頁上那個雜湊因此不只是「我們那次建置的紀錄」,任何人都能自己算出來。

打包腳本會對照釘住的雜湊驗證官方 CPython,對不上就刪掉下載檔並中止 —— 一個產 SBOM 的工具沒有立場用未經驗證的位元組建置自己。
