1.10.0 2026-09-14 目前版本

逐區段判定加密,不再讓空白區拉低整體判斷

一份韌體映像不是均質的。一個 64 MB 的 flash dump 可能只裝著 3.6 MB 的 加密 kernel,其餘全是抹除過的空白 flash。整份一起量,空白區會 壓過密文 —— 熵值算出來只有 0.74,判定「明文」,SBOM 於是說這份 韌體是明文而且沒有任何元件。

真相是它唯一的內容區段根本讀不出來。 把「讀不到」報成「裡面沒有東西」,正是這個工具存在的理由要防止的 事。

修正

每個區段現在各自判定。同一份映像:kernel 熵值 7.9999、最長同值位元組 連續 3、2083 個重複的 16-byte 對齊區塊 —— 判定為加密,並產生一個標記 offset、大小與判定依據的 opaque 元件。空白區段被認出是抹除過的 flash, 不再計入判斷。

報告還會寫明:「整份一起量會得到『明文』(熵值 0.736);那個數字被沒有 內容的區域主導了。」讓讀的人知道為什麼天真的量法會出錯。

  • 重複區塊視為加密模式訊號 —— 相同的明文區塊加密成相同的密文區塊,是 ECB 模式的特徵。這比「熵值很高」對讀報告的人有用得多。
  • 每個讀不出來的區段各自成為一個元件 —— 帶 offset、大小、熵值與判定依據,而不是整份映像一個籠統的標記。

讀取根檔案系統裡的每一個檔案

之前根檔案系統只有兩個資訊來源:套件資料庫,以及二進位檔的中繼資料。 裡面的檔案本身從來沒有被掃描過。對 OpenWrt 這種有完整 套件記錄的裝置影響不大;但大多數廠商韌體根本沒有套件資料庫,那些映像 的根檔案系統因此一個元件都產生不出來。

  • 逐檔簽章比對 —— 掃描沒有被任何套件認領的檔案。套件管理員的記錄對它涵蓋的檔案是權威的,在上面再疊啟發式判斷只會增加雜訊;它沒涵蓋的部分才是新資訊。沒有套件資料庫的裝置,那就是每一個檔案。
  • 證據指向實際檔案 —— 命中會記錄它來自哪一個檔案路徑。稽核人員可以去看 /usr/sbin/dropbear;「payload 的 offset 0x3f1a80」則什麼也做不了。
  • 區分可執行檔與其他檔案 —— 編譯進二進位檔的版本 banner,與設定檔裡的一行版本註記,證據力不同。文件不應該讓它們看起來一樣。

以手上那台 router 模擬「沒有套件資料庫」來驗證:根檔案系統由 0 個元件變成 9 個帶檔案歸屬的元件,版本以套件資料庫作為對照全部正確 —— BusyBox 1.35.0、curl 7.88.1、zlib 1.2.11、U-Boot 2022.01。

修正

證據原本引用的是該元件字母序第一個檔案,不一定是產生那句 引文的檔案。實測中 OpenSSL 的版本引文來自 /usr/bin/openssl, 文件卻指向一個 YAML 設定檔。在稽核文件裡指錯檔案不是外觀問題。

讀取韌體裡的二進位檔

套件資料庫說明了安裝了什麼,但沒說這個映像是什麼架構、誰真的連結了誰, 而在完全沒有套件資料庫的裝置上,它什麼也沒說。新的 ELF reader 回答這三件事。

  • 指令集識別 —— Linux 映像沒有向量表可以辨認,之前一律回報「未識別」;每個 ELF header 都寫明了。
  • 真正的依賴圖 —— 兩個獨立來源:套件管理員宣告的 Depends(意圖),與 linker 寫進每個 binary 的 DT_NEEDED(實際連結的證據)。兩者都沒有的套件就沒有出邊,不會替它編一條。
  • 宣告的授權 —— 359 個套件中 262 個帶 SPDX 授權識別碼,進入 CycloneDX 的 licenses 欄位。
  • 廠商宣告的 CPE —— OpenWrt 自己在套件記錄裡標註了 54 個 CPE,正好是與 CVE 最相關的那批。fw2sbom 讀取這個宣告並標記來源 —— 這與猜一個 CPE 出來是兩回事。
  • Kernel module 中繼資料 —— 192 個模組的宣告版本與授權。

效能:讀 467 個 binary 原本要 12.0 秒,幾乎全部花在重複解壓同一批 SquashFS fragment block(小檔案共用它們)。加了有上限的快取之後是 0.68 秒。

授權與第三方歸屬

分析行為完全沒變,只是加了授權檔並讓它們隨套件一起交付。

修正

套件裡本來只有一份授權檔,而且是 Python 的。客戶解壓後看到 LICENSE.txt(PSF)擺在我們的原始碼旁邊,沒有任何東西說明哪份 條款管哪些檔案 —— 這種歧義出現在一個做合規的產品身上特別說不過去。

兩份授權現在都會交付,我們那份刻意改名為 LICENSE-fw2sbom.txt, 不能蓋過直譯器自己那份。覆蓋掉你再散布的軟體的授權檔, 正是這個工具在別人韌體裡要抓的錯誤。打包流程也加了檢查: LICENSE.txt 不見了就直接中止。

Linux 裝置韌體:從 0 個元件到 366 個

一台真實的 GL.iNet router 之前產生零個元件。判定是對的 ——「compressed」—— 而 SBOM 是空的,因為 Linux 裝置映像裡值得命名的東西 全都在壓縮區段內,掃描器只看到它的外殼。

  • 容器走訪 —— U-Boot uImage 檔頭、任意位置的壓縮區段、SquashFS superblock,每個區段獨立分析。解壓支援 gzip / xz / lzma / bzip2。lzo / lz4 / zstd 沒有標準函式庫實作,會明確報告「未展開」並指名演算法,不會靜默跳過。
  • SquashFS 4.0 reader —— 唯讀,純標準函式庫。真實 12 MB rootfs 走訪 3,274 個檔案用 0.02 秒。
  • 套件資料庫(opkg / dpkg / apk)—— Linux 韌體 SBOM 品質的主要來源:不是從二進位猜版本,而是套件管理員自己的安裝紀錄。359 個套件,全部帶精確版本。

找到的包括 OpenWrt 22.03.4、Linux 5.10.176、BusyBox 1.35.0、OpenSSL 1.1.1t、 dropbear 2022.82、curl 7.88.1、zlib 1.2.11。

修正

gcc-arm-none-eabi 這個簽章會在任何 GCC 編譯的 映像上命中,包括 MIPS —— 它最高權重的比對樣式是通用的 GCC 版本字串, 與簽章的名字完全不符。在稽核文件裡寫「這台 MIPS router 用 arm-none-eabi 工具鏈」是一句錯的陳述。通用的那一半已拆成獨立的 gcc 簽章。

1.6.0 2026-09-11

SPDX 2.3 輸出,以及不再猜測版本

  • SPDX 2.3 JSON —— 與 CycloneDX 由同一次分析產生,所以兩份文件不可能互相矛盾。兩者都通過各自規格的官方 schema 驗證。
  • --firmware-version —— 產品自己的韌體版本寫入 SBOM 根 component。只有客戶知道這個值,而 CRA 場景需要跨版本追蹤同一個產品。
  • 版本策略 —— 有些元件在剝除符號的映像裡結構上就沒有版本字串 (nrfx 與 nRF5 DFU 只留下 API 符號名,已對真實裝置映像確認)。為這些元件發明一個 比對樣式,正是這個工具拒絕做的猜測。改成:沒有版本樣式的簽章必須附上 version_note 說明為什麼不可能有,以及該去哪裡取得版本 —— 這個要求 假樣式滿足不了,讀的人也查得到。

測試安全網與簽章外部化

分析流程是一疊啟發式判斷,而啟發式的失敗是無聲的:一個不再命中的常數 只會產生比較小的 SBOM,不會產生錯誤,沒有人會發現,直到客戶的報告是錯的。

  • 56 個 regression 測試,涵蓋 9 份即時合成的韌體映像(固定 seed,byte-identical 可重現)。
  • CycloneDX 1.6 schema 驗證 —— 這個輸出之前從未驗證過。
  • CI —— Ubuntu 與 Windows 雙平台;另一個 job 把套件建置兩次並比對雜湊,讓「可重現」由聲稱變成每次推送都驗證的事實。
  • 簽章外部化 —— 移到 signatures/*.json,載入時驗證。完全找不到簽章包時工具直接結束,不會產生一份空的 SBOM:「資料庫沒送到」不可以長得像「這份韌體沒有元件」。
  • UTF-16LE 字串萃取 —— 之前只讀 ASCII。
新測試揭發的兩個錯誤

判定與元件清單自相矛盾。opacity 判定在簽章比對之前執行, 所以它可以一邊印「無法識別元件」,一邊列出 8 個帶精確版本的元件。 現在證據贏過統計。

UTF-16 字串會偷走前一個 ASCII 字串的最後一個字元 (NUL 結尾讓它看起來像 UTF-16 單元)。證據會逐字引用命中字串進稽核文件, 所以這不能留。

可重現的打包流程

套件現在由腳本產生,而且是可重現的:entry 排序、timestamp 與壓縮等級全部固定,所以同一個原始碼版本重新打包會得到位元組完全相同的檔案。 下載頁上那個雜湊因此不只是「我們那次建置的紀錄」,任何人都能自己算出來。

打包腳本會對照釘住的雜湊驗證官方 CPython,對不上就刪掉下載檔並中止 —— 一個產 SBOM 的工具沒有立場用未經驗證的位元組建置自己。
