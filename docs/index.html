先核對,再執行

這個套件刻意不含任何我們自己編譯的執行檔 —— 裡面只有 python.org 官方發佈的直譯器,加上我們的 Python 原始碼。所以它不會觸發 Windows SmartScreen 的「未知發行者」警告,但也因此沒有數位簽章可以驗。 請改用雜湊核對:

這個套件是可重現的:同一個原始碼版本、同一個官方 CPython, 任何人在任何機器上重新打包都會得到位元組完全相同的檔案,因此也會得到上面 這個雜湊。它不只是「我們那次 build 的紀錄」。

它看得懂什麼

這張表寫的是實際覆蓋範圍,不是規劃。標為「部分」或「未支援」的,工具會 明確講出來,不會產生一份看起來完整的空 SBOM。

IoT / MCU 裝置ARM Cortex-M · MCS-51
支援
向量表架構識別、廠商 packetized / ISP-dump 格式自動去框、加密映像判定、 內嵌標準資料(VESA E-EDID、DDC/CI MCCS)。Zephyr、FreeRTOS、mbed TLS、 lwIP、MCUboot、littlefs、Nordic 與 STM32 SDK 等 36 組簽章。
Router / GatewayLinux · MIPS / ARM
支援
U-Boot uImage 檔頭、壓縮 kernel(gzip / xz / lzma / bzip2)、SquashFS 4.0 根檔案系統。直接讀出 opkg / dpkg / apk 套件資料庫, 得到每個已安裝套件的精確版本。FIT / TRX 與廠商自訂檔頭尚未支援。
CCTV / NVRLinux · 專有 SoC
部分
使用標準 uImage + SquashFS 的機型與 router 相同。廠商自訂容器需逐個支援; 整段加密的機型會被判定為 opaque 並如實標記,需要向供應商索取原廠 SBOM。
PC BIOS / UEFIx86 · EDK2
未支援
Flash Descriptor / Firmware Volume / FFS 解析尚未實作。目前分析這類映像 會回報「未識別架構」,不會產生誤導性的結果。

一台真實的 router

GL.iNet GL-MT300N-V2,OpenWrt 22.03.4,MIPS,14.6 MB。整份映像只有檔頭是明文, kernel 是 LZMA、根檔案系統是 xz —— 直接掃字串會得到零個元件。

$ fw2sbom openwrt-mt300n-v2-4.3.25.bin -d out/ --format both [fw2sbom] segment 0x00000000 U-Boot uImage header (Linux/mips) (expanded) [fw2sbom] segment 0x00000040 Linux kernel (lzma) (expanded) [fw2sbom] segment 0x0023ec0d SquashFS 4.0 (xz) (read) [fw2sbom] distribution: OpenWrt 22.03.4 r20123-38ccc47687 [fw2sbom] 359 package(s) from /usr/lib/opkg/status (opkg), 359 with exact versions [fw2sbom] 366 component(s) identified [fw2sbom] linux-kernel version=5.10.176 confidence=0.97 (high) [fw2sbom] gnu-binutils version=2.37 confidence=0.95 (high) [fw2sbom] gcc version=11.2.0 confidence=0.9 (high)

這 359 個套件的版本不是從二進位猜出來的,而是讀自映像裡套件管理器自己的 安裝紀錄 —— 包含 BusyBox 1.35.0、OpenSSL 1.1.1t、dropbear 2022.82、 curl 7.88.1、zlib 1.2.11。這是 Linux 裝置 SBOM 品質的主要來源。

你會拿到什麼

兩種 SBOM 格式

CycloneDX 1.6 與 SPDX 2.3,由同一次分析產生,所以兩份 文件不可能互相矛盾。兩者都通過各自規格的官方 schema 驗證。

  • CycloneDX 有為 binary-derived SBOM 設計的 evidence 物件,confidence 與命中證據都能結構化表達
  • SPDX 2.3 沒有對應欄位,那些資訊會放進 annotations 與 comment,文件本身會註明以 CycloneDX 為準

一份人看的證據報告

七張工作表的 Excel 檔,給稽核人員而不是機器看。裡面同時記錄 負面證據。

  • 掃描過但未命中的每一個簽章 —— 「我們找過 BusyBox,它不在裡面」本身就是一項發現
  • 被判定為誤報的弱 magic 命中,以及判定理由
  • 逐 64 KiB bank 的熵值與雜湊、掃描覆蓋率、EDID 設定檔

三個步驟

01

解壓縮

把 zip 解到任何資料夾。裡面是一個完整的 Python 執行環境,不會動到系統。

02

雙擊啟動

執行 Start-fw2sbom.bat。終端機視窗會顯示服務狀態,瀏覽器自動開啟。

listening on http://127.0.0.1:8765/
03

把韌體拖進去

分析完成後下載 SBOM 與證據報告。關閉終端機視窗即停止服務。

這是 binary-derived SBOM

元件與版本是從已編譯的映像推斷出來的,不是從建置系統的清單讀來的。判定為 啟發式,可能不完整或有誤 —— 「沒偵測到」不等於「不存在」。 Confidence 上限刻意設在 0.97,永遠不會是 1.0。

映像加密時,工具會產生一個標記為 opaque 的元件並說明判定依據,而不是交出一份 空的 SBOM。「無法分析」與「沒有元件」必須是兩件不同的事。
